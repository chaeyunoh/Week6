## 실패가 불량 응답보다 적은 이유

불량 응답 5건 중 코드펜스형과 사족형 3건은 방어 코드가 복구하여 정상 처리했고, 잘린 JSON형 2건만 실패로 집계되었다. 따라서 실패 건수(2건)는 불량 응답 건수(5건)보다 적으며 잘림 건수와 같다.

## 방어 코드별 처리

| 불량 유형 | 처리 방어 | 결과 |
|---|---|---|
| 코드펜스 | 방어 1 (``` 제거) | 복구 |
| 사족 | 방어 1-2 (첫 `{`부터 마지막 `}`까지 추출, find/rfind 사용) | 복구 |
| 잘림 | 방어 0 (`stop_reason == "max_tokens"` 확인) | 실패 |

사족 복구를 적용하지 않았다면 이 실행의 실패는 4건(사족 2 + 잘림 2)이었고, 적용 후 2건으로 2건 줄었다.

## 잘린 JSON을 복구할 수 없는 이유

잘린 응답은 일부 필드와 닫는 중괄호(`}`)가 잘려 나가 불완전한 JSON이 된다.
예: `{"category": "배송", "sent` (여기서 끊김)

`json.loads()`는 완전한 JSON만 파싱할 수 있어서 불완전한 문자열은 예외를 던진다.
`find` / `rfind`로 `{`~`}` 범위를 추출하려 해도 `}`가 없으면 추출 자체가 불가능하다.
따라서 방어 코드가 잘림을 **사전에 감지**(stop_reason == "max_tokens")해 실패로 처리하는 것이 최선이며,
근본적인 해결책은 `max_tokens` 값을 충분히 늘려 잘림 자체가 발생하지 않도록 하는 것이다.
